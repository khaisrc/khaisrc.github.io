# AGENTS.md

## Repository overview

This repository contains Khai Nguyen's personal engineering portfolio, built as a static Astro site and deployed to GitHub Pages. The site currently presents professional projects as case studies; a blog may be added later.

## Working principles

- Preserve unrelated user changes. Check `git status --short` before editing and do not revert, overwrite, or stage work you did not create.
- Treat `src/` and `public/` as source. Do not hand-edit generated content in `dist/` or `.astro/`.
- Keep changes focused and follow existing Astro, TypeScript, HTML, and CSS patterns before introducing new abstractions or dependencies.
- Use accessible semantic markup, keyboard-visible focus states, descriptive link labels, and appropriate ARIA attributes.
- Keep the site static and compatible with GitHub Pages unless a task explicitly changes the deployment model.
- Every generated text file must end with exactly one newline, not two.

## Project structure

- `src/pages/`: Astro routes. Project detail pages are generated by `src/pages/case-studies/[slug].astro`.
- `src/components/`: Reusable Astro components for project lists, cards, and filters.
- `src/layouts/BaseLayout.astro`: Shared document shell, metadata, header, and footer.
- `src/styles/global.css`: Global design tokens, layout rules, component styles, and responsive behavior.
- `src/content/case-studies/`: Markdown project case studies.
- `src/content.config.ts`: Astro content schema; update it deliberately when content fields change.
- `public/`: Static assets copied as-is into the build.
- `scripts/validate-content.mjs`: Privacy and placeholder checks for source and generated output.
- `scripts/check-links.mjs`: Internal-link validation against the built site.
- `.github/workflows/static.yml`: GitHub Pages build and deployment from `master`.

## Commands

Use the repository's npm scripts:

```sh
npm install
npm run dev
npm run check
npm run validate
npm run build
npm run preview
```

- Run `npm run check` for Astro and TypeScript validation during development.
- Run `npm run validate` after changing source content.
- Run `npm run build` before handing off substantive changes. It performs Astro checks, source validation, a production build, generated-output validation, and internal-link checks.
- If validation fails because of pre-existing missing or modified files, report that clearly; do not restore those files without authorization.

## Case-study content

Add case studies as Markdown or MDX files in `src/content/case-studies/`. The filename becomes the URL slug. Frontmatter must satisfy `src/content.config.ts` and currently includes:

- `title`, `company`, `role`, `summary`, and `description`
- `techStack` and `areas` as non-empty string arrays
- `metrics` as an array of `{ value, label, context? }` entries; use `[]` when no defensible metric is available
- `featured` and `draft` booleans
- `order` as a unique positive integer controlling display order
- `confidentialityReviewed: true`
- Optional `companyUrl` and `period`

Follow the established narrative structure where it fits: `Problem`, `Contribution`, `Technical approach`, `Outcome`, and `Engineering judgment`. Write in first person for individual contributions, distinguish personal work from team outcomes, and prefer specific evidence over promotional language.

Do not publish confidential or personally identifying information. Source and output validation reject email addresses, phone numbers, local user paths, internal ticket identifiers, and unfinished placeholders such as `TBD` or `TODO`. Do not weaken these checks merely to make content pass; rewrite or remove sensitive content instead.

## UI and styling conventions

- Reuse the design tokens in `:root` and existing utility/component classes in `src/styles/global.css`.
- Keep the current editorial/technical visual language unless the task requests a redesign.
- Verify layouts at narrow mobile widths and desktop widths after meaningful UI changes.
- Preserve canonical URLs, metadata, sitemap integration, and trailing-slash-compatible internal routes.
- Use `@lucide/astro` for interface icons already represented by that library; icons must not be the only accessible label.

## Completion checklist

Before handing off a change:

1. Review `git diff` and confirm only intended files changed.
2. Run the narrowest relevant checks while iterating.
3. Run `npm run build` for substantive code, content, routing, or styling changes when the current worktree permits it.
4. Report checks run, any failures, and any pre-existing worktree conditions that affected verification.
